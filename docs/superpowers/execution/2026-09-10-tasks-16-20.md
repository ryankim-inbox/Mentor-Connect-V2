## 실행 시 판단과 비용

1. 이전 격리 worktree에서 검증한 `35faaac6`을 이어 사용했다. 외부 Python 변경을 합치지 않으므로 이후 최신 main 통합과 검증이 따로 필요하다.
2. 사용자 요청에 따라 독립 파일 작업은 병렬화하고 gateway·package·lock·Vite 수정은 순서대로 인계한다. commit은 조정자가 전담한다. 판단이 틀리면 통합 재작업 비용이 발생한다.
3. spec의 audit-only 문장은 이전 계획 작성 단계의 범위로 해석하고 현재 Task 16–20 실행 요청에 따라 구현한다. 잘못 해석했더라도 변경은 격리 branch에서 되돌릴 수 있다.
4. readiness·WS·UI의 로컬 동작을 구현하되 provider staging·실제 배포 결과는 미확인으로 남긴다. 출시 전 실제 origin·읽기 전용 credential·startup 재시도·TLS와 배포 검증이 필요하다.
5. Task 17의 gateway 검토 전에 독립 WebSocket module·test를 먼저 구현한다. 검증된 callback 인터페이스를 사용하고 실제 gateway 연결은 Task 17 이후로 미룬다. 인터페이스가 바뀌면 tunnel 연결 부분을 조정해야 한다.

6. 비용이 큰 매칭의 두 GET 경로·POST `/api/matches`·위치 실습 POST는 사용자별 분당 12회 제한을 공유한다. 호출 경로를 바꿔 같은 계산을 반복하는 우회를 막고 정보 조회·채팅 polling은 제외한다. 제한이 과하면 빠른 연속 실습이 최대 60초 기다려야 하므로 사용량을 보고 조정할 수 있다.

7. startup 버전은 빌드한 metadata에서 읽고, 아직 빌드하지 않은 개발 실행은 `unknown`을 기록한다. metadata 누락·오류가 readiness 성공으로 이어지지는 않는다. 개발 로그에 commit이 필요하면 먼저 빌드해야 하고, production은 metadata 산출물과 readiness 통과가 필요하다.
