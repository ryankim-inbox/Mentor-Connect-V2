- macOS arm64 PostgreSQL 16.13, Linux x64 PostgreSQL 16.15.
- macOS와 Linux의 clean `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm build:release`, 기존 DB suite 통과.
- Python runtime lock SHA-256: `6bac2bf38641d479a031988307bdffaa4b28e1cdf28ebaaced9deeb572ec16ec`. 독립 출력 디렉터리와 두 플랫폼에서 동일했다.

## 운영 시 남은 확인

- 별도 provider classroom DB/credential 및 SESSION_SECRET 발급·저장·교체 증빙.
- 암호화된 provider 저장소에 snapshot 보관, 최근 7개 retention, 실제 provider 복구 측정.
- Replit production build 산출물 `.release-runtime`이 run 단계에 보존되는지 실제 배포에서 확인하고 필요한 uv 버전을 제공한다.
- backup/restore는 명시적으로 `disable` 또는 `verify-full`만 지원한다. provider URL의 `require`/`prefer`/`verify-ca`는 그대로 사용할 수 없으며 검증 가능한 TLS·CA 설정으로 운영자가 명시적으로 조정해야 한다. 옵션 생략은 TLS 비활성화다.
- 기존 Vite tooltip sourcemap 진단은 build를 막지 않으며 이번 범위 밖의 기존 경고다.

WS tunnel은 Task 18, 전체 production UI 공개는 Task 20을 포함한 후속 작업이다. Task 16–24는 실행하지 않았다. 학생의 TODO/실패 응답을 TypeScript 성공 데이터로 바꾸지 않았다.

## 실행 중 결정과 비용

1. 사용자 요청에 따라 병렬 subagent를 사용하고 파일 소유권을 분리했다. commit은 조정자가 전담했다. 순차 구현이라는 skill 기본값보다 명시적 요청을 따랐으며, 판단이 틀리면 통합 재작업 비용이 발생한다.
2. 원격 교실 DB와 provider 증빙이 제공되지 않아 로컬·운영 도구를 구현하고 원격 secret·저장소·배포 결과는 미확인으로 남겼다. 실제 출시 전에 운영자 작업이 남는 비용이 있다.
3. spec의 audit-only 문장은 이전 계획 작성 단계의 범위로 해석하고, 현재 Task 11–15 실행 요청에 따라 구현했다. 잘못 해석했더라도 변경은 별도 로컬 branch에서 되돌릴 수 있다.
4. 실제 bootstrap/seed와 임시 DB 검사가 통과한 뒤, Task 13 최종 검토와 Task 14 구현을 병렬로 진행했다. 공유 파일은 순서대로 인계했다. Task 13 인터페이스가 바뀌면 Task 14를 조정해야 하는 비용이 있다.
5. `pnpm-workspace.yaml`은 기존 `minimumReleaseAge: 1440`과 platform 정책이 요구사항을 충족하고 두 플랫폼 build도 통과해 그대로 두었다. 계획의 파일 목록만을 위한 무효 수정은 생략했으며, 추후 platform 문제가 나오면 필요한 override를 추가해야 한다.
6. Task 13 예시보다 DB 대상과 빈 DB 검사를 강화했다. 실제 드라이버가 소비하는 주소를 검증하고 같은 lock 안에서 사용자 object가 있는 DB를 거부한다. 특이한 이름이나 기존 object가 있는 DB는 거부될 수 있어 명시적으로 빈 교실 DB가 필요하다.
7. Node pg와 native libpq의 TLS 해석을 맞추기 위해 backup/restore는 `disable`·`verify-full`로 제한했다. `require`·`prefer`·`verify-ca` provider URL은 그대로 쓸 수 없고 운영자가 CA와 검증 옵션을 명시적으로 맞춰야 한다.
