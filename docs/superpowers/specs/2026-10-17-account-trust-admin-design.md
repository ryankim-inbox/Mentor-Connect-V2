# Account trust and administrative access design

The user authorized local implementation after a short design/risk/test report. No deployment, remote database changes, remote pushes, real email, provider signup, paid resources, or credentials are authorized in this phase. Mobile work is excluded. Work starts from merged PR23 (f3972b1046a80b454c6a5e62c84cca9d625c54dd) in a separate worktree.

## Product boundary
The existing `/recommendations` Matches page accepts arbitrary question IDs and displays Python engine diagnostics. Practice, analytics, scheduling and report pages are exposed to every signed-in student. This mismatch was reported before edits. Keep those operational pages administrator-only. Give students a separate `/mentors` directory with safe public mentor fields, current-district and block filtering, and links to existing profiles and request/application workflows. Do not remove student request creation, application, acceptance, connections, or chat.

Student role remains mentor/mentee/both. A separate `is_admin` database flag grants administrative access; clients can never grant it. Check current database identity/verification/admin state server-side, including direct backend calls. Anonymous requests get 401, authenticated insufficient privileges get 403. Operational GET and mutation routes are admin-only; public health/readiness stays operationally usable and reveals no private state. Keep public district list and landing-page aggregate counts. Private user fields are self-only; peers receive a minimal member projection.

## Email ownership
Add `email_verified_at` and an explicit `is_admin=false` default. Existing `is_verified=true` only represented the old .edu suffix check and is not ownership proof: migration sets legacy users unverified without deleting data. New accounts start unverified. `isVerified` is derived from ownership proof and synchronized with matching's legacy boolean. Login and own profile/settings, verification request/consume and logout are available unverified. Require verification for member data/actions, chat and all admin features, including WS opening and messages after revocation.

Verification uses cryptographically random 32-byte opaque tokens, SHA-256 digests at rest, 30-minute expiry, atomic single use, and last-token-wins resend. Verification consumes a token only for the logged-in account/email. Resend is at most once per 60 seconds and five requests per rolling hour per account, persisted in PostgreSQL; use gateway network limits as a second layer. Never place token values in logs or ordinary API responses. Confirmation links use a configured trusted origin, put token in the URL fragment, and require an explicit confirmation action (GET must not consume). No email-changing feature is introduced.

Use a mail-delivery interface with disabled production default and an explicitly enabled development file outbox (0600 files in a 0700 directory), unavailable when NODE_ENV=production. Tests may inspect this local outbox. No actual sending implementation or provider credentials now. Failed delivery must not claim success; allow controlled retry without invalidating a previously delivered token. Bound token history/storage and invalid attempts. Document operator steps to select a provider and verify/admin-provision accounts later without running those steps.

## Community safety
Reuse blocks and reports. Provide block/report actions on member profiles and an unblock list in settings. Keep bilateral restrictions for DMs/applications/interactions. Reports have bounded reason/description; ordinary users can submit, but only verified admins can read report content or update status. Admin moderation status: open, reviewing, resolved, dismissed; store actor and timestamp, optional bounded internal note. Return no report descriptions to students.

Own comments can be edited and deleted. Use soft-deletion tombstones so others' replies remain. Deleted text must not appear in list, mutation responses, idempotent replay, or parent previews. Reject editing deleted comments; do not resurrect via duplicate clientCommentId. Changes require authorship, request visibility and existing block rules. Keep chronological ordering stable; show edited/deleted state. Students cannot edit/delete others' comments, including an owner deleting a comment by another author.

## Risks and verification
Legacy accounts become unverified on eventual migration, requiring coordinated mail-provider rollout; this branch is not deploy-ready until that is configured. No existing admin is auto-promoted. Schema 0006 must preserve all existing content and immutable migrations 0001–0005, with upgrade tests and regenerated schema catalog/manifest. Test expiry/replay/resend races, concurrent confirmation, delivery failure, token secrecy, forged user/admin/verification attributes, post-login role revocation, blocked peers, and cross-account access.

Exercise anonymous, unverified, mentor, mentee, both and admin through both backend and gateway. Verify admin menus and direct routes, GET and mutation APIs, safe profile projection, student mentor discovery/application acceptance, own-comment changes with retained replies, and report privacy. Run targeted red/green tests, full local Python/gateway/UI/schema/contract suites, typecheck/build, independent review, and document failures or unrun checks separately. Live production validation is excluded in this phase.
